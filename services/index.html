Who I work with

The kind of project that fits

Not every project is a good match, and it saves us both time to say so up front.

Small businesses and professionals

You need a site that explains what you do and gets people to contact you — and you would rather it loaded quickly and looked current than came with a page builder you have to learn.

Early-stage startups

You have a product idea and need the first working version built: accounts, a dashboard, an API and a database, put together so the second version does not mean starting again.

Teams with an existing site

What I do not do I am one developer, not an agency — so I do not take on brand identity design, ad campaigns, SEO retainers, or projects that need a team of five starting next week. If that is what you need, I will say so rather than take the work and subcontract it.

Custom website development

A website designed and coded for your business rather than assembled from a theme — so it says what you need it to say, loads fast, and works on the phone most of your visitors are holding.

What it is

A hand-built, responsive company or marketing website: home, services, about, contact, and whatever else your business actually needs. Built with React, or with plain HTML, CSS and JavaScript when a framework would only add weight.

Who it is for

Businesses, consultants, clinics, studios, agencies and professionals who currently have no site, a dated one, or a social media page doing a website's job.

The problem it solves

People search for you, find nothing convincing, and go to a competitor instead. A site that looks credible and answers the obvious questions turns that search into an enquiry.

What you get

  • Responsive layouts checked from a 360px phone up to a wide desktop
  • Clean page titles, descriptions and heading structure
  • A working contact route — form, email and WhatsApp
  • Deployment, plus the source code handed over to you

Custom web application development

Software that runs in a browser and does a job: logins, roles, records, dashboards, reports. The thing a website cannot do.

What it is

A full stack application — React on the front end, Node.js and Express behind it, MongoDB storing the data — with authentication, permissions, validated APIs and an interface built around the workflow your users follow.

Who it is for

Startups building a first product, and businesses running an operation on spreadsheets, WhatsApp groups and memory that has outgrown all three.

The problem it solves

Work gets lost between tools. Nobody can say who is doing what, what is overdue, or what happened last month, because there is no single place the answer lives.

What you get

  • JWT authentication with role-based access
  • REST APIs with validation, pagination and consistent error handling
  • A MongoDB schema designed for the queries you will actually run
  • An admin area, and a deployment path that survives the first change

React.js development

Front-end work in React, whether that is the whole interface or a specific part of one that already exists.

What it is

React interfaces built as reusable, config-driven components, with React Router for navigation and Redux Toolkit where the state genuinely needs it — plus the API wiring underneath, using Axios.

Who it is for

Teams with a design and no front-end developer, founders who need a React front end built against an API that already exists, and anyone who has inherited a React codebase nobody wants to touch.

The problem it solves

A front end where every new screen is copied from the last one gets slower to change every month. Components built to be reused reverse that.

What you get

  • Component structure another developer can pick up
  • Protected routes and authentication flows wired properly
  • Interfaces that hold together at every screen width
  • Code splitting and lazy loading where they earn their place

MERN stack & full stack development

MongoDB, Express, React and Node — one stack, one language, one developer across all four layers.

What it is

End-to-end delivery: database schema, REST API, React front end and deployment, built as one system rather than three pieces handed between people. Full stack development and MERN development describe the same work here.

Who it is for

Anyone who needs a working product rather than a component of one, and who does not want to coordinate a front-end freelancer, a back-end freelancer and a designer who have never spoken to each other.

The problem it solves

Split ownership is where projects stall: the front end waits on an API, the API waits on a schema decision, and nobody is accountable for the gap between them.

What you get

  • One person accountable from schema to deployed site
  • JavaScript throughout, so shared logic is not written twice
  • Real-time features with Socket.IO when a project needs them
  • Environment-driven config, so local and production run the same build

AI-powered web applications

AI inside a product that has a job to do — scoring, analysis, generated feedback — rather than a chatbot bolted onto the corner of the screen.

What it is

Web applications that call AI APIs as part of a workflow: a document goes in, an analysis or a score comes back, and the result is stored, displayed and acted on inside the app.

Who it is for

Products where a person currently reads, grades or summarises something by hand, and that step has become the bottleneck.

The problem it solves

AI features fail in production for unglamorous reasons: the API is slow, rate-limited or down. The engineering that matters is what happens then.

What you get

  • AI calls isolated in their own service layer, not scattered through the app
  • Graceful fallbacks, so an outage degrades the feature instead of the product
  • Results stored and reportable, not thrown away after display
  • API keys kept server-side, never shipped to the browser

Admin dashboards

The screen your team actually spends the day in: users, records, orders, tasks — searchable, filterable and permission-aware.

What it is

A React admin interface over your data, with protected routes per role, tables that page and sort on the server, dialogs for create and edit, and charts that answer a specific question.

Who it is for

Businesses whose operations data lives somewhere a customer should never see, and whose staff currently manage it through a spreadsheet or a database client.

The problem it solves

Without an admin area, every content change, refund or correction has to go through a developer. That is slow for you and expensive for both of us.

What you get

  • Role-based access, so staff see only what they should
  • Server-side pagination, search and sorting that stay fast as data grows
  • A record of who changed what, and when
  • Charts and counts tied to real questions, not decoration

API & backend development

The half your users never see, built so the half they do see stays reliable.

What it is

REST APIs on Node.js and Express, MongoDB schema design with Mongoose, JWT authentication, role-based authorisation, request validation and consistent error responses — documented rather than guessed at.

Who it is for

Teams with a front end or a mobile app and no back end, and products where the API is the thing being sold.

The problem it solves

An API that returns a different shape on every endpoint, and a stack trace when something fails, makes every client that consumes it harder to build.

What you get

  • Endpoints with predictable request and response shapes
  • Authentication and per-role authorisation enforced at the route
  • Validation on the way in, one error handler on the way out
  • A schema designed for the queries you will actually run
